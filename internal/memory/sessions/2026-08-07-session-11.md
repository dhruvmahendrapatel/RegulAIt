## Slice E specifically

Its scope was **corrected before briefing**, and that correction is the most useful thing this
session produced. The plan's original paragraph described building importers for proxy logs, CASB
exports and SSO reports — nearly all of which ADR-0055 already had: four evidence kinds
(`egress_log`, `code_scan`, `saas_export`, `self_reported`), dry-run/apply, payload SHA-256,
per-row provenance, forbidden-key stripping, honest refusal.

The real gap was one layer lower: **ADR-0055 accepts rows already normalised to its zod schemas**,
so a customer had to reshape their own export by hand. Nothing read a raw CEF line or a W3C proxy
log. That made Slice E an *adapter slice*, not a subsystem — five adapters on ADR-0069's registry
playbook, feeding the existing pipeline.

Two decisions in it worth keeping:

- **No migration.** `shadow_ai_imports.summary` is already `jsonb NOT NULL` and nothing queries
  imports by adapter, so 0083 was never created. A migration that exists only to look thorough is
  a liability.
- **No vendor-named adapters**, asserted by a test. ADR-0069 shipped declared-header vendor presets
  and then named them its own biggest gap. Putting a vendor's name — the part a buyer actually
  trusts — on a format nobody here has seen repeats that mistake deliberately.

## What this session got wrong, and what that cost

**I recommended building something that already existed.** Slice D was scoped from the plan file
rather than the codebase, and its headline item — an OpenAI-compatible endpoint — had shipped in
ADR-0024. Semantic caching had shipped too. Three of five listed gaps were not gaps.

The fix became a standing rule, applied to every slice afterwards and written into the plan file so
it outlives this conversation: **verify the premise against the codebase before writing the brief.**
It immediately paid for itself on Slice E, which was mostly already built.

This is the same failure as session 07's: asserting a gap with more confidence than the evidence
supported. Session 07 was about competitors; this was about our own repo. The lesson generalises —
*check, then claim.*

## Two CI failures, both real bugs, both the same root cause

Neither was flake. Both were **a test picking a DB row by position out of a query with no
`ORDER BY`**:

1. `workflow-stage-quorum` took the first pending gate approval rather than the caller's own. Under
   quorum `all` there is one row per approver, so ana decided bob's approval and the platform
   correctly returned 403. Passed locally for months; failed the first time Postgres returned the
   rows the other way round.
2. `governance-gaps` took `after[after.length - 1]` as "the row this call just wrote". **The count
   assertion passed either way, which is exactly what made it look sound** — counting how many rows
   appeared and picking which row appeared are different questions, and only the first was answered.

Both fixed by identifying rows by identity rather than position, plus a deterministic `ORDER BY` on
the affected route (an API returning a list in unspecified order is a wart for anything rendering
the approval queue, quite apart from having hidden this).

**A sweep found six more test files with the same landmine** — `pii`, `guardrails`,
`compliance-packs`, `copilot`, `gateway-parity`, `ide-interception`: ~78 `db.select()` calls and
**one** `orderBy` between them. Deliberately **not** fixed: changing six files unverified at the
tail of a wave trades one known failure for several unknown ones. Offered to the owner as a
dedicated pass.

## The verification method, since it kept finding things

Every slice was verified by this session on a **freshly created database**, never by re-reading the
authoring agent's report. Seven adversarial tests were added whose job is to make the central claim
**non-vacuous** — each asserts both that the thing works *and* that a plausible fake would fail:

- `learning-is-real` — generalize on signal AND score near chance on noise. A memorizer passes the
  first and fails the second; constant weights fail the first.
- `groundedness-is-real` — grounded vs fabricated over *identical* context, gap > 0.4.
- `asr-is-real` — the interval must widen as N shrinks and stay non-zero-width at 0/N and N/N.
- `no-blend` — every number at every depth, including numbers inside sentences; 13.13 + 86.87 = 100
  appears nowhere.
- `cef-escaping-is-real` — the parser handles escaped separators AND `String.split` gets the same
  input wrong.

A one-sided assertion is the failure mode worth guarding against: a function that reported nothing
would satisfy "the blend never appears."

Also caught: two agent claims that were overstated rather than wrong — "the core mentions tracing
nowhere" (it takes a defaulted sink parameter plus two comments) and, in an earlier wave, an unfair
test comparison. Neither changed a verdict; both are worth the habit.

## Standing caveats that did not change

- **No model provider is connected.** Judge metrics, probe grading and MRM-backed behaviour remain
  mechanism-proven and instrument-unverified. The owner's key stays parked by standing instruction.
- **Nothing has been run against a live vendor endpoint** — training adapters, cost-import vendor
  presets, the OTLP collector, and every evidence-format adapter are spec-shaped and unit-tested.
- **Foot-gun**: the red-team scheduled sweep has no `trials` override and inherits the pair's last
  run, so a one-off 25-trial investigation costs 25× on every subsequent sweep.
- Local Postgres died twice during this session; `service postgresql start` and re-run. A `psql`
  failure hidden by output suppression cost real time — do not suppress it.
