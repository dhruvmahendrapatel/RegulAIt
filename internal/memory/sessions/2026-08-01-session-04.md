## The three defects this session surfaced

All three shared one cause: **something shipped without ever being executed in its real
environment.** Recording them because the pattern matters more than the individual bugs.

### 1. The `tls` compose profile had never once started

Shipped in #77; never exercised end-to-end on the box. Caddy pins `172.28.0.2` so
`REGULAIT_TRUSTED_PROXIES` can name exactly one container (ADR-0031) — but **pinning an address
does not reserve it.** Docker allocates dynamically from the start of the subnet, and Caddy is
necessarily *last* to start (gateway waits on db's healthcheck; Caddy waits on the gateway). `db`
took `172.28.0.2`; Caddy died with:

```
Error response from daemon: Address already in use
```

which reads as a host **port** conflict, not an IPAM one — `ss -lntp` showed nothing on 80 or 443,
and db and gateway were both healthy. Because ADR-0029 binds the gateway to host loopback only,
the result was a box with **no route in at all**.

Fixed (#88) with `ip_range: 172.28.1.0/24`, confining dynamic allocation clear of the pinned
address. Verified before/after on the box: `db` moved `172.28.0.2` → `172.28.1.0`, Caddy took
`172.28.0.2`, `compose up rc=0`.

### 2. CI's very first run caught a latent test bug

All **881 tests passed** and the job still exited 1. `seed.test.ts` tears down its scratch database
with `DROP DATABASE ... WITH (FORCE)`, which force-terminates whatever connection is still open,
raising Postgres `57P01` (`admin_shutdown`) as an unhandled pool error — which vitest counts and
fails on. Latent for weeks **precisely because CI was off**, and it would have red-failed every
future PR. Being fixed at the leak, not suppressed with an error handler or a vitest flag.

### 3. ADR-0032's `aws:SourceArn` confused-deputy guard does not work

Every `CreateSchedule` failed with:

```
ValidationException: The execution role you provide must allow AWS EventBridge Scheduler
to assume the role.
```

This reads **exactly** like IAM propagation lag. It is not — it survived four separate applies over
roughly thirty minutes, each retrying internally for 2m10s. Bisected against live API calls:

| Trust policy condition | `CreateSchedule` |
|---|---|
| none | PASS |
| `StringEquals aws:SourceAccount` | **PASS** |
| `ArnLike aws:SourceArn` (even `schedule/<group>/*`) | FAIL |
| `ArnLikeIfExists aws:SourceArn` | FAIL |

`CreateSchedule` validates the trust relationship *before the schedule exists*, and satisfies no
`aws:SourceArn` condition in any form — **including `...IfExists`, whose entire purpose is to
tolerate an absent context key.**

**A trap worth knowing:** the validation verdict appears to be cached per-role for a minute or two,
so back-to-back probes return the *previous* policy's answer. Two intermediate readings in this
session were initially misread that way, and the wrong conclusion was drawn twice before the
caching became apparent. Allow ~75s between changing a trust policy and believing a result.

Guard dropped (#90), with the cost written into the ADR rather than glossed: cross-account
confused-deputy is still blocked; **intra-account narrowing is given up**; the compensating control
is the permission policy — exactly `StartInstances`/`StopInstances` on exactly the passed instance
ARNs, no `Terminate`, no wildcard resource.

## The public IP moved twice in one day

`3.237.199.248` → `98.86.163.252` → `3.229.246.126`

The first move was **self-inflicted and non-obvious**: the terraform apply changed `user_data`, and
the EC2 provider applies that by stopping and starting the instance, which releases an
auto-assigned public IPv4. The second was Elastic-IP attachment. Since the hostname is
`<dashed-ip>.sslip.io`, each move silently broke both the URL and its certificate.

Now pinned by an EIP (ADR-0032), and `infra/scripts/boot-resync.sh` re-points Caddy on every boot
regardless. On its first run it also re-enabled swap and wrote the `/etc/fstab` entry user-data
never did — cloud-init's `scripts-user` is per-*instance*, never per-boot.

**Rule for future sessions: any `user_data` edit is an instance restart, and on this stack that is
an address change.**

## Legacy UI: blocked twice, correctly

The first deletion was reverted (`95a3bc1`) because ADR-0026 asserted "parity, zero gaps" with no
evidence and five capabilities were legacy-only. This session's capability diff found **six more**:
rules deploy-mode scoping, revocation narrowing, and four run-detail operator controls (manual node
dispatch, `reassign_node`, `node_submitted`, per-node instruction override) — i.e. the SPA could
only drive a run fully automatically and could not rescue a stranded node.

The agent asked to do the deletion **refused and reported**, which was the right call. Gaps closed
in #89, which also promoted the checker into the repo (`scripts/parity-diff.mjs` +
`legacy-ui-parity.test.ts`) comparing **three** dimensions — endpoint shapes, run event kinds
POSTed, and request-body keys — because an endpoint list alone cannot see gaps of the last two
kinds. It also found the original throwaway extractor's comment stripper would treat `text/*`
inside a string as a block comment and eat the rest of the file: **it could report false parity.**

## Still open

- **Postgres has no backup.** It is a container volume on one EC2 instance that now power-cycles
  nightly by design. Nightly `pg_dump` → S3 with a *tested restore* costs pennies and is the
  largest single unmitigated risk on the board.
- **HSTS contradicts ADR-0029.** The ADR argues carefully that an ephemeral-IP-derived hostname
  must not be HSTS-pinned, and Caddy honours that — but responses carry
  `Strict-Transport-Security: max-age=31536000; includeSubDomains` because **the gateway sets it**.
  Needs a decision about which layer owns the header. Raised to the owner, not decided unilaterally.
- No real model provider connected. The owner's key stays parked until they raise it.
