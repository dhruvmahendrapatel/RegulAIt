## A. Discovery coverage

**1. What does RegulAIt actually scan?**
Only the sources an admin adds and enables: GitHub, GitLab, Bitbucket and Azure DevOps repositories; AWS, Azure and
GCP accounts; and endpoints, through an osquery pack, an MDM/EDR export or the RegulAIt endpoint agent (ADR-0195;
`packages/shared/src/discovery/index.ts`). Everything is read-only and every source starts disabled. In today's live
demo the laptop is an imported inventory export, not the agent: the agent's signed collection-pack stage is pending,
so the prepared copy's agent reports were seeded (owner, 2026-10-24; ADR-0197 addendum of that date). Evidence you
already hold (egress logs, SaaS exports, code scans, self-reported lists) can still be imported alongside (ADR-0055,
ADR-0071).

**2. What does it look for in a cloud account?**
AI services only. On AWS: the managed-model and model-serving resources in each enabled region, and the audit log's
model-invocation events grouped by calling principal; on Azure: the hosted AI accounts and their deployments, the
machine-learning workspaces, and the activity log (ADR-0195 decision 16). Each run lists
which reads it could and could not make, for example a log that is not enabled.

**3. What does it look for in a repository?**
AI SDK dependencies and imports, endpoint references, IDE extension configs, MCP server configs, key fragments, and
the AI-related environment-variable names in templates such as `.env.example`, Dockerfiles and CI files (ADR-0195
SD1, lane A6). It keeps the matched signature, the path and line, the commit, and the commit author as a pseudonym.
Commit history is not scanned unless an admin turns it on, which is a relaxation.

**4. And on a laptop?**
Installed AI desktop apps, IDE and browser extensions, local model runtimes and their listening ports, AI command-line
tools, and the names of AI-related environment variables and config files (ADR-0195 decisions 18-19). No keystrokes,
screenshots, clipboard, file contents, prompts or browsing history; with no agent, an MDM/EDR inventory export gives
the installed apps and extensions only. The agent is built for Linux; Windows is built and unit-tested but not yet
enrolled on a real host and has no installer; macOS needs the Secure Enclave build, which is pending; and no real
agent reports yet, because the gateway serves no signed collection pack until that stage exists (ADR-0195 SD4g;
`agents/endpoint/internal/devicekey/platform_darwin.go`). The customer distributes the agent through their MDM;
RegulAIt never installs it.

**5. Does an empty inventory mean we have no shadow AI?**
No. The page says so in its own words: *"this inventory reduces shadow AI — it does not prove its absence"*
(`coverageScorecard`, `packages/shared/src/shadow-ai.ts`). The **Coverage** tab lists, per evidence class, what it
sees and what it misses, and each scan run lists its catalogue gaps.

**6. How do you avoid false positives?**
A finding exists only when an observation matches an enabled row of your own signature catalogue, and each row carries
its provenance and confidence (ADR-0083 §3; ADR-0195 SD0). Every finding is a lead: an admin records a disposition
(confirmed, sanctioned, false positive, remediated) with a required reason, and a finding seen again after a
disposition is flagged "seen again since". Lower-confidence signatures are labelled in the sighting lines under the **Evidence** column (*▶ n places*; "Where seen" joined Evidence in #477).

**7. How often does it scan?**
On an admin-set schedule, daily by default and hourly at the shortest, and on demand (ADR-0195 decision 9). Runs are
leased, so a crashed worker's run is retried rather than lost or doubled, and each provider is rate-limited with
back-off. Endpoint sources are fed by uploads, so they have no schedule.

**8. Is detection proof that someone broke policy?**
No: detection is a signal, not proof. A sanctioned tool and a shadow one can look the same from outside, which is why
the row says what was seen and where, and a person decides what it means.

## B. Data handled

**9. Do you store our code, prompts or secrets?**
No scanner stores file contents, prompt or response content, or a full secret (ADR-0195 decision 6). Raw scanner
output is digested with SHA-256 and discarded. A detected key is kept only as its 8-character redacted prefix and
where it was found, and a scanner never calls a provider to test a key it found.

**10. You match environment variables. Do you keep their names or values?**
Neither. The names are matched on the spot against presence signatures, and only the signature ids are stored as
evidence (ADR-0195 lane A6, `SightingView.presence` in
`apps/web/src/views/admin/governance/discoverySourcesModel.ts`). Values are never read into evidence; on a laptop,
key values are redacted on the device before anything is sent (decision 19).

**11. Do findings name employees?**
Not by default. Commit authors, cloud calling principals, devices and device users appear as `psn:` plus a keyed hash
with a per-tenant key (ADR-0195 decision 20). The real name is stored encrypted under the data key; revealing it asks
the admin to confirm it is them and is audited. Employee-monitoring law varies by country, so we ship an employee
notice template and recommend legal advice before enabling endpoint discovery
(`docs/deployment/ENDPOINT_EMPLOYEE_NOTICE_TEMPLATE.md`).

**12. How long is evidence kept?**
Endpoint evidence: 90 days by default, and lengthening it is an audited relaxation (ADR-0195 decision 20). Shortening
it is free. Other retention follows the deployment's audit-retention policy.

**13. Where is the data in the demo from?**
The live accounts are ours: a GitLab demo group, a non-production AWS sandbox account and an Azure subscription,
with AI usage we planted under fictional names and no personal data (ADR-0197 decisions 2-5 and 8), plus an inventory
export of one of our demo laptops, imported. The scans and the import are real; the endpoint agent's reports exist
only on the prepared copy, where they were seeded.

## C. Credentials and keyless federation

**14. What credential does RegulAIt hold for our cloud?**
None that lasts. AWS and Azure sources are federated: RegulAIt mints a five-minute RS256 token from its own issuer, and
your IAM role or Entra app registration trusts that issuer (ADR-0195 SD2b;
`packages/shared/src/discovery/federation.ts`). No long-lived cloud secret is stored. The issuer's discovery
document and key set must be reachable from the cloud provider (ADR-0197 decision 3). It is not the workload-identity
issuer: the federation issuer is `<REGULAIT_PUBLIC_URL>/federation`, with its own RS256 keys and key set, separate from
the Ed25519 workload-identity issuer (ADR-0188), so a token from one never verifies at the other.

**15. Who creates the IAM role?**
You do. The read-only permission set each adapter needs is published as a document and as infrastructure-as-code you
apply in your own account; RegulAIt never creates IAM in a customer account (ADR-0195 decision 17;
`docs/deployment/CLOUD_DISCOVERY.md`).

**16. What if the credential we give you can write?**
Where the provider lets us check, a credential that grants write access is refused, never used again, and the source
cannot run until it is replaced (ADR-0195 decision 7). Where it cannot be checked, the posture page says "write scope
unverified". Storing a static secret instead of federation is itself a relaxation the posture page lists.

**17. Is git scanning keyless too?**
For two providers, yes: GitHub and Azure DevOps sources federate by default (built; not yet run against a live
account). GitHub goes through the deployment's GitHub App and a short-lived, read-only installation token; Azure DevOps
exchanges a five-minute RegulAIt federation token at Entra. GitLab and Bitbucket accept no third-party token for their
APIs, so they use a read-only access token, stored encrypted and never returned, which the posture page lists as a
relaxation (`docs/deployment/GIT_DISCOVERY_CREDENTIALS.md`). The demo's GitLab group is that case.

**18. Can RegulAIt reach anywhere it likes from inside our network?**
No. Every scanner call goes through the egress allow list, and cloud and git API hosts are added by an admin when a
source is enabled, not shipped pre-allowed (ADR-0195 decision 8, ADR-0034).

## D. Deployment: air-gapped and BYOC

**19. Does discovery work air-gapped?**
Partly, by design. Repository scanning works against self-hosted git, and the endpoint options work unchanged; cloud
scanning works only through your private endpoints for the cloud APIs (ADR-0195 decision 10). With none configured,
each cloud read the egress guard refuses is reported on the run as `unreachable`, read by read; there is no separate
air-gapped source state (`packages/cloud-discovery/src/types.ts`, `CapabilityStatus`).

**20. Air-gapped installs and release signing?**
An install records its deploy mode, and on `air_gapped` the gateway refuses any model, connector, git or PM adapter
that would call its built-in vendor endpoint unless that host is on the egress allow list (`scripts/install.sh`,
`REGULAIT_DEPLOY_MODE`, ADR-0062). Update bundles are Ed25519-signed and verified offline against a pinned keyring
(ADR-0041), but no air-gapped install has been run end to end yet, and the offline image bundle does not yet carry the
object store (`scripts/build-image-bundle.sh` saves the gateway, Postgres and Caddy). Engine images are signed keylessly in CI, and the repository carries their signatures and trust root
(`engines/signatures/`); on an air-gapped install, `scripts/install.sh` refuses an engine image whose signature does not
verify. The endpoint agent's packages are still built unsigned today (`agents/endpoint/README.md`).

**21. BYOC?**
BYOC is the primary motion: one single-tenant deployment per organisation, in your cloud account, under your IAM and
your key (ADR-0041; `scripts/install.sh --mode byoc`, `docs/deployment/INSTALL.md`). Automated deployment of governed
workloads into AWS, Azure or GCP is partial and flag-gated off today (ROADMAP, Batch C).

**22. What crosses from your control plane to our environment?**
The disclosed data boundary is in `docs/deployment/DATA_BOUNDARY.md`. Scanners send findings (locations, names,
pseudonyms, digests) to your own deployment, and the endpoint agent sends signed reports only to your
organisation's gateway (ADR-0195 decision 19).

## E. Provider-agnosticism

**23. Do you only work with one cloud or one model vendor?**
No. Discovery covers three clouds and four git providers (`DISCOVERY_SOURCE_KINDS`), and the governed path routes to
any vendor's models, open-weight or in-house endpoints, with per-user entitlement independent of vendor (ADR-0034,
`packages/model-provider/src/index.ts`). The demo uses AWS and Azure because those are the accounts we planted;
GCP uses the same interface.

**24. What if a provider you do not know shows up?**
Detection is data: an admin adds a row to the signature catalogue, with its provenance, without a release (ADR-0083
§3). Unmatched observations appear per run as catalogue gaps, so a new provider is visible before anyone writes a
signature for it.

**25. Are you tied to one PM or git tool for the remediation workflow?**
No. The remediation runs through the same workflow engine as every other change, and the engine works across GitHub,
GitLab, Bitbucket and Azure DevOps, with PM adapters for Azure DevOps, Jira, Linear, Asana and monday.com
(`resolvePmProvider` in `packages/pm-provider/src/index.ts`; the PM-tool row of `internal/product/ROADMAP.md`).

## F. From finding to governance

**26. Does RegulAIt shut down shadow AI automatically?**
No. It proposes a remediation plan; starting the plan's workflow is a person's act, the workflow is plan-only until a
person finishes planning, and its sign-off must come from an admin other than the person who started it (ADR-0195
A4; `apps/gateway/src/shadow-ai-remediation.ts`). If no second admin exists, the workflow does not start. In the
demo, the security lead signs off what the governance admin started.

**27. Can an admin relax that?**
Yes, audited: retiring the shipped default template lets the admin's own assignment rule decide, and an admin who
wants the initiator to sign off authors their own template through the audited template path
(`shadow-ai-remediation.ts`). The default stays strict (owner decision Q7).

**28. What does "Register as use case" carry over?**
Only the name and the observed use. Every EU AI Act screening answer is left blank for the proposer, because the
finding does not establish them (`IntakeWizardPage.tsx`, ADR-0085).

**29. How do we know the remediation worked?**
The finding is linked to its workflow and marked confirmed under the admin's name. The panel's "loop closes" line
names the evidence to look for: the next call from that subject in the audit log and usage ledger instead of outside
it (`ShadowRemediationPanel.tsx`). Closing the finding is then a person's disposition on that evidence, with a reason;
nothing marks it remediated automatically. A finding seen again after a disposition is flagged.

## G. Content trust (if the optional beat is shown)

**30. You detect prompt injection. Is that enough?**
Detection alone is not a defence, so every MCP server and connector starts untrusted, and a write is refused when the
run already holds content from a source below the write floor (ADR-0193; `ContentTrustPage.tsx`). Each governed
result is recorded by its source, tier and digests, never its content. We make no claim about any legal
content-marking duty.

## H. The demo itself

**31. What was real and what was mocked?**
The scans of our planted accounts are real (LIVE path), and the live database holds only what they found. If we
switched to the prepared copy (the same product on the presenting laptop), its discovery data was seeded through the
product's real API paths, and its GitLab, AWS and Azure runs are recorded replays through the real discovery worker
(ADR-0197 decision 7 and addendum). On screen, only the *(demo dataset)* suffix on each source name marks that data,
which is why we said so aloud. Governed model traffic uses keyless mock agents
through the real dispatch path, and every page, workflow, approval and alert is live product code. Any recording or
screenshot we show, we say so.

**32. Can we see it on our own estate?**
Yes, read-only: a proof of concept adds your sources disabled, you apply the read-only role in your own account, and
an admin enables each source with a step-up. We recommend starting with one repository group and one cloud account.

## I. Enterprise and procurement

Added 2026-10-24 (owner decision, #453 comment 6385378784, item 4; full-scan FS-9): the standard evaluator questions,
from the scan's drafted answers, each checked against the file it cites. Where the honest answer has a weak spot, the
weak spot is in the answer.

**34. Prove default-deny.**
With no grant there is no call: the policy kernel returns `deny` with the rule `default-deny` and the chain of every
rule it walked, for tools, agents and connectors alike, and an approval rule never rescues an ungranted call
(`packages/policy-kernel/src/index.ts`). `tools/list` is filtered to what the person may see. Beat E shows the kernel's
decision for one denied and one approval-bound call on the Simulation page, which executes nothing; the refusal of a
real call lands in the audit log the same way, named by its rule.

**35. What happens when your gateway is down or slow?**
Governed calls do not happen: dispatch runs strictly after the decision (`packages/model-provider/src/index.ts`), an
evaluation error refuses (`apps/gateway/src/abac.ts`), and the optimisation layers fail open to the un-optimised path
and say so in the trace (`apps/gateway/src/compaction.ts`). Today a deployment is one gateway process and one
Postgres; high availability is deployment work on the roadmap (ROADMAP Batch F), not a claim. We fail closed by
construction.

**36. Can a developer call the model vendor directly and go round you?**
Key custody is the control: the provider keys live in the gateway, and a user-supplied credential is refused at
dispatch, so no key means no call. What goes round anyway, discovery is built to find. We prevent with key custody and
your own egress policy and detect with discovery; we do not claim network interception (ROADMAP §8.1).

**37. Which parts are real and which are simulated?**
The scanners ran against real accounts on the live path, the governed model traffic uses keyless mock agents, and the
PM adapters (Azure DevOps, Jira, Linear, Asana, monday.com and a generic webhook) are real HTTP clients with verified
inbound webhooks (`packages/pm-provider/src/index.ts`). Automated BYOC deployment of workloads is partial and
flag-gated off (`apps/gateway/src/deploy.ts`). Answer 31 says what was real in this demo.

**38. BYOC and air-gapped: what can you show?**
`scripts/install.sh --mode byoc|air_gapped` with bundle and signature preflight; no call to us at runtime, verifiable
by reading the data boundary (`docs/deployment/DATA_BOUNDARY.md`); licences verified offline. No customer has run the
air-gapped path, and the offline image bundle does not yet carry the object store, so the round trip is the next
operations item (answer 20).

**39. How accurate is cost attribution?**
Each call's cost is the provider's measured usage times the served agent's list price; an unpriced agent records
null, never an estimate (`packages/model-provider/src/index.ts`, `apps/gateway/src/agents-connectors.ts`). Provider
invoices can be imported and reconciled without overwriting the ledger (`apps/gateway/src/cost-reconcile.ts`). The
demo's economy is a mock provider's.

**40. Can a worker agent do more than the person who started the run?**
No. Every node of a run is decided with the initiating person's grants through the same evaluation, a lead agent can
only narrow what it delegates, and delegation beyond the person is refused
(`packages/orchestration-kernel/src/index.ts`; `apps/gateway/src/orchestration.ts`). It is not in today's demo.

**41. Are the PM integrations two-way, and what happens on a conflict?**
Work items and transitions go out, verified webhooks come in, and drift is detected on every report. The conflict
policy is per connection: manual by default, or prefer the PM tool or prefer RegulAIt, each resolution audited with
before and after (`apps/gateway/src/pm-drift-resolution.test.ts`). Approval decisions are mirrored to the work item.

**42. Is the audit trail tamper-proof, and how long is it kept?**
It is tamper-evident with external anchors: a hash chain whose head is anchored to an Object Lock COMPLIANCE store and
graded by asking the store itself; a GOVERNANCE-mode or unreadable store grades false, and unanchored rows are
disclosed on every verify (`apps/gateway/src/audit-chain.ts`). The signed bundle verifies offline
(`scripts/verify-export-bundle.sh`). Retention is a floor composed from the compliance profiles, and pruning is off by
default. We do not call it immutable.

**43. Where does our data live?**
In a single-tenant deployment, one per organisation, with its own database (`apps/gateway/src/org-settings.ts`). If we
host it, we hold the disk, and the data boundary document says so (`docs/deployment/DATA_BOUNDARY.md`). Today's demo
runs on our own development instance.

**44. Are we locked to one model vendor?**
No. The model layer has adapters for several commercial vendors' APIs, custom endpoints for open-weight or in-house
models, in-house artifacts and a keyless mock (`packages/model-provider/src/index.ts`). Entitlement is per person and
independent of vendor, and the gateway flags when the model a provider actually served drifts from the one approved
(`apps/gateway/src/agents-connectors.ts`).

**45. SSO, SCIM and MFA?**
OIDC and SAML sign-in, an SSO-only mode with a break-glass account the product will not let you lock out
(`apps/gateway/src/sso-providers.ts`, `apps/gateway/src/break-glass.ts`), SCIM 2.0 provisioning on its own trust path
(`apps/gateway/src/scim.test.ts`), TOTP required for admins, and a 30-minute idle limit by default. The demo does not
open the SSO settings page; answer from here.

**46. What is open source, and under which licences?**
The product is proprietary (`LICENSE`); each package lists its third-party components in its `THIRD_PARTY.md`, with
no copyleft licence in shipped code (ADR-0176). Licences are verified offline, and a deployment with no licence runs
with the tier features closed. Two permissive licences in the dependency closure are outside the written list today
and are being admitted by an ADR-0176 amendment (full-scan FS-22).

**47. Certifications, references, production customers?**
None held, nothing in production, and the usage in today's demo was planted in our own accounts
(`internal/product/POSITIONING.md` §6). What we have is a repository where every claim links to its decision record and
its test, and a ledger of our own mistakes kept in the open.

**48. What is not built?**
Automated deployment of governed workloads into a cloud account, multi-tenant hosting, network-level bypass prevention
and high availability (ROADMAP §2 and Batch F); the endpoint agent's macOS device key, its signed packages and its
signed collection pack are pending (answer 4).

**49. Is the inventory on screen real or seeded?**
On the live path it is real: `demo:check --live` fails closed on any trace of the fictional dataset
(`apps/gateway/src/demo-check-lib.ts`). On the prepared copy, the only on-screen marker is the *(demo dataset)* suffix
on each source name, which is why we say it aloud.

**50. Does remediation close by itself when the app moves behind the gateway?**
No. A person records the finding's disposition on the evidence in the audit log and usage ledger, with a reason, and a
finding seen again after that is flagged (answer 29).

**51. Is the endpoint agent employee monitoring? What does it send?**
Catalogue ids, relative paths, ports and key names, with key presence only; a privacy guard refuses any report that
contains a home path or a user or host name (ADR-0195 decisions 19-20), and an employee-notice template ships
(`docs/deployment/ENDPOINT_EMPLOYEE_NOTICE_TEMPLATE.md`). Its packages are built, not signed
(`agents/endpoint/README.md`).
