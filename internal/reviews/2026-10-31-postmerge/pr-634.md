## P7R-01 — HIGH: mutate the existing scorer to bypass detector relaxation step-up

Locations: `apps/gateway/src/trained-detectors.ts:270-274`; `packages/shared/src/trained-detectors.ts:170-171`; `apps/gateway/src/external-scorers.ts:308-350`, `:426-444`.

ADR-0220 decision 6 explicitly treats switching an enabled detector's scorer as a relaxation because an otherwise valid service may always answer zero. The detector PUT protects a change of `scorerId`, but the referenced scorer remains mutable through the old external-scorer PATCH. Moving its base URL only disables it pending a connection test; PATCH, test and re-enable have no `settings_relax` requirement. Thus a stolen admin API key, which cannot complete the required fresh human step-up, can replace the detector's instrument while keeping the same scorer id. Both destinations can be on an already approved host, so no egress relaxation is needed.

Reproduction with the real Fastify app and an admin API key, strict `stepUpMode=required`, own PostgreSQL database and two loopback scoring services:

1. Enable the injection detector at block, pointing to service A (score 0.99); an ordinary input blocks.
2. PUT the detector's mode to warn using the admin API key: **403 `step_up_required`**, confirming the ceremony is effective.
3. PATCH `/v1/external-scorers/:id` to service B's URL: **200**.
4. POST its `/test`: **200**; POST its `/enabled` with enabled=true: **200**.
5. Run the identical guardrail input under a freshly resolved policy: **allow** (service B scores 0.01), without presenting any step-up token.

The same mutable dependency also permits credential changes without disabling/retesting, which can change instrument behavior at one URL. This was inspected, not separately tested.

Fix: guard every security-relevant mutation of a scorer used by an enabled trained detector (endpoint, transport allowance, credential and claimed kinds) with a value-bound settings-relax step-up, or refuse it until the detector is disabled through its own guarded path. Serialize the scorer reference check and mutation against detector updates, so a concurrent binding cannot bypass it. Add a route-level negative regression covering the full PATCH/test/enable sequence with an admin API key.

## P7R-02 — MEDIUM: trained PII findings do not inherit the effective PII block floor

Locations: `apps/gateway/src/guardrails.ts:325-328`, `:342-347`; `packages/shared/src/trained-detectors.ts:198-219`.

The policy resolver deliberately forces `modes.pii = off` to avoid double-running the heuristic PII detector. The trained planner reuses that same modes map and consequently runs trained PII at only the configured row mode. The real PII mode is resolved separately by `projectPiiMode` and never passed into trained planning. A trained detector at warn/log therefore returns a trained PII finding as warn/log even when the organisation's strict default or the project's compliance cascade requires PII block. The old heuristic path can miss the person-name/address categories for which the trained recogniser was introduced.

The standalone probe asserts `await projectPiiMode(db,null) === 'block'`, configures trained PII mode warn, receives score 0.99 on ordinary text containing a fictional name, and obtains **action=warn**, not block. No heuristic finding is present, so no dedicated-path block compensates. This is a policy composition gap relative to ADR-0220 decision 4's effective-mode inheritance, not an assertion about the quality of the actual model.

Fix: keep the heuristic's PII exclusion separate from trained planning. Carry the effective cascade PII mode into trained PII planning, MAX-compose it with the row's mode, and use the same result for streaming buffering. Add org-default and classified-project regressions where the trained model is the only detector finding the personal data. If the owner intends independent PII policy despite a cascade block, document and decide that divergence explicitly instead of claiming inherited mode.

## Known limitation, not presented as a new finding

`agents/trained-detectors/server.py:71` truncates each classifier input at 512 tokens while `detector_core.py:26` chunks by 1,500 characters. Dense tokenization can leave a suffix entirely unscanned. `agents/trained-detectors/README.md:53-55` already discloses this and records token/stride windows as a follow-up. Security consequence: a classifier's clean score is not complete coverage of all accepted text. No real weights/tokenizers were downloaded in this review, so no real-model evasion claim is made.
