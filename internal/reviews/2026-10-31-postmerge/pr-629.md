## SUP-01 — MEDIUM: a stale partial settings update can undo a security tightening without step-up

Location: `apps/gateway/src/supplier-portal.ts:310-334`.

The handler reads both settings outside its transaction, substitutes stale current values for omitted request fields, decides whether step-up is required, and then writes both values without a lock/re-read or a compare-and-set guard. An update that only tightens file acceptance can therefore overwrite a concurrent portal-disable with `enabled=true`. No enabling action was requested or authenticated with step-up. The audit records an empty relaxation list and only the file-setting change, hiding the restored access state.

Bounded local proof: start with both settings true and step-up required. Hold the org-settings row lock, send the authenticated admin's `{acceptUnscannedFiles:false}` PUT, and confirm the route has reached its blocked UPDATE. Commit a concurrent portal-disable, then release the lock. The pending request returns 200 and persists `{enabled:true,acceptUnscannedFiles:false}`; its audit has `relaxed:[]`. The inverse lost update can restore acceptance of unscanned files when a concurrent request tightens that setting.

Fix: serialize settings read, transition classification, write and audit against a current locked row. If the state changes after validating a value-bound step-up, refuse with a retry/conflict rather than using stale authorization. Only write requested fields. Add two interleaving regressions, covering each setting being tightened concurrently.

## SUP-02 — MEDIUM: an in-flight supplier upload commits after its session and grant are revoked

Location: `apps/gateway/src/supplier-portal.ts:1180-1208` and `:1248-1266`; revoke handling at `:730-757`.

Submission validates the session and grant before awaiting the scanner. Its transaction later locks the grant for quota enforcement but never checks that the now-locked grant/session is still active. Revocation can finish during that await, invalidate the session, and reject every pending answer, after which the old request inserts a new answer and file as `submitted`.

Proof through the full Fastify app and real database: start an authenticated supplier submission with a controlled scanner paused at its await; revoke the grant through the admin endpoint and wait for its 200 response; resume the scanner. The old supplier request returns 201 and a new `submitted` row with file ciphertext survives. The separate normal revocation tests still pass because they start the next request after revocation, rather than overlapping it. No external services or real supplier data were used.

Fix: inside the submission transaction, re-read and validate the live grant and session after obtaining the serialization lock, including expiry/revocation and the current assessment/portal state. Use a lock order shared with revoke/settings paths so validation cannot be followed by a security transition before commit. A revoked/expired session must leave no new answer, file, or submission audit row.
