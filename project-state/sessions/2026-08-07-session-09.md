# Session 09 — 2026-08-07 — Parity Slice C: cross-vendor cost consolidation (ADR-0069, migration 0081)

Append-only. Never edited retroactively.

## What was asked for

Build **Slice C** of [COMPETITIVE_PARITY_PLAN.md](../../docs/product/COMPETITIVE_PARITY_PLAN.md) §1
— the one gap session 07's competitive research found **genuinely unserved by any incumbent**:
consolidating one human's spend across Claude Code seats + Copilot seats + a raw OpenAI key + a
Bedrock account into a single per-person figure an FP&A team can charge back.

The brief named the reason it is unserved, and it is also the reason it is hard:

> Per-seat SaaS spend is invoice-side, not call-side — which is exactly why the incumbents skip it,
> and exactly why doing it honestly matters more than doing it impressively.

## What the gap actually was

Confirmed by grep before writing anything: no invoice/usage-export importer, no vendor-account →
RegulAIt-user identity resolution, and — the load-bearing one — **no `metered` vs `imported`
distinction anywhere in the cost model**. Every figure in the product was implicitly metered with
nothing to say so, which meant there was no place to put a restated number that would not
immediately be mistaken for an observed one.

## Decisions worth remembering

**1. The blended total does not exist, as a matter of type.** The temptation here is enormous:
imported + metered is the number every buyer asks for, it is one line of code, and refusing it looks
like a missing feature. It was refused. `consolidate()`'s return type has no field for the sum, no
route computes one, and **both** suites walk the entire response body — every number at every depth,
including numbers spelled inside sentences — asserting the blend appears nowhere. The fixture
numbers were chosen so a coincidence is arithmetically impossible (61.11 + 146.30 = 207.41, which
arises no other way). If a future session adds a convenience `total`, four tests fail.

**2. The distinction is a CHECK constraint, not a convention.** Imported money lives in its own
table with `basis` pinned to `'imported'` in the database. The alternative — a column on
`usage_events` — would have been less code and was rejected because every existing query,
statement, forecast and budget check reads that table and none of them would have learned to filter.
One missed `WHERE` puts an unverifiable restated figure inside a customer's invoice. The suite
proves the constraint by attempting the lie and requiring the insert to throw.

**3. The PII exemption is real and is disclosed rather than hidden.** A vendor export is a list of
employee emails; that is not incidental PII, it is the join key. Running the default `block`-mode
ADR-0042 gate over the account column would make the feature impossible rather than safe. So the
account column is exempt **by construction**, every other retained free-text field goes through the
identical `detectPII` + `evaluateGuardrails` + `effectiveIngestMode` path ADR-0065's training ingest
uses, and the exemption is stated in the code, in every import response, on the adapter registry and
in the ADR. Asserted from both directions: an SSN in a *description* column blocks the import; an
email in the *account* column does not.

**4. There is no scheduled re-import, and the absence is argued rather than assumed.** ADR-0064's
scheduler exists and everything else periodic uses it. There is nothing to poll: RegulAIt holds no
vendor billing-API credential, and minting one is an egress decision (ADR-0034/0062), a
credential-custody decision (ADR-0063) and a per-vendor API-shape decision — each larger than this
slice. A job whose only possible action is "re-read a file nobody uploaded" reports success while
doing nothing. What shipped instead is **staleness reporting** on the consolidated view (per-vendor
`lastImportedAt` + `daysSinceLastImport` + a note saying why), mirroring ADR-0055's coverage
scorecard.

**5. Only one CSV parser exists in the codebase, still.** Row-number-accurate refusals needed a
reader that keeps physical line numbers and does not drop blank records — but rather than write a
second parser, `parseCsvRecords` was added *beneath* `onboarding.ts`'s `parseCsv` and `parseCsv` was
redefined in terms of it. Its existing tests were untouched and still pass.

**6. Ambiguity is refused everywhere it appears.** `07/08/2026` is refused (a wrong guess silently
moves spend between reporting periods). Header inference refuses when both `cost` and `total` are
present. Two domain rules that resolve one account to two different people resolve it to nobody. An
empty amount is refused because an absent measurement is not zero. A line over $1bn is refused
because a cents-as-dollars units error is more common than a real charge that size.

**7. An unmatched account is a first-class outcome, not an error.** It is retained, shown as its own
unattributed subject sorted last, and **never** spread pro-rata across the people who did match —
which is the most-requested chargeback feature and manufactures a number for every person on the
list. Asserted: 10/90 stays 10 and 90, not 100 and not 55.

**8. Deleting a user un-attributes their spend rather than deleting it.** `ON DELETE SET NULL` alone
would have violated the `resolution_method`/`resolved_user_id` pairing CHECK and made users
undeletable, so a `BEFORE UPDATE` trigger stamps the method back to `unresolved` and records that
the prior attribution was to a now-deleted person. A chargeback report that silently shrinks when
somebody leaves is a broken report.

## What shipped

- **Migration 0081** — `cost_import_batches` (planned/applied/refused/**revoked**, with
  `rows_parsed = rows_accepted + rows_refused` as a CHECK and a **partial unique index on
  `payload_sha256` over applied batches** as the double-count guard), `imported_cost_lines` (with
  the `basis` CHECK and the resolution-pairing CHECK), `vendor_account_aliases`,
  `vendor_domain_rules`, and `users.cost_center` — the person-level chargeback key that
  `projects.cost_center` could never be for a seat charge.
- **`packages/shared/src/cost-import.ts`** — the adapter interface + registry (five adapters, each
  declaring capabilities *and* an honest `limits` string the API returns), character-scanned
  amount/date/currency parsers, the identity-resolution rules, and the consolidation math.
- **`apps/gateway/src/cost-import.ts`** — eleven routes, all admin-only through the existing
  default-deny gate except `GET /v1/users/:userId/cost-consolidated`, which refuses in-handler
  unless the caller is that user.
- **ADR-0069**, the README index row, and Slice C marked SHIPPED in the parity plan with its
  "read this before citing it" note.

## Verification

Fresh DB, full suites. Gateway **1859 → 1889 tests / 108 → 109 files**; shared **427 → 477**;
policy-kernel 129, model-provider 122, infra-provider 174, training-provider 58 — all unchanged.
`pnpm -r build`, `pnpm --filter @regulait/web build` and `pnpm -r typecheck` clean.

The openapi drift-detection tests (ADR-0053) caught the new routes immediately, exactly as designed
— they were added to `ROUTE_STABILITY` and `ROUTE_TAGS` as `internal`, because adding a vendor
adapter changes the accepted `adapter` values and a public-stable contract would freeze that list.

## Disclosed rather than closed

Every one of these is in ADR-0069's "What this explicitly does NOT give you", in the parity plan's
note, and in the README row:

- **The three vendor presets are built against DECLARED header sets, never verified against a live
  console by anyone here.** This is the largest honest gap in the slice. They refuse the file naming
  the missing column rather than mis-parsing, and `generic_mapped` is the escape hatch — but a
  first-time user should expect to check. **The owner's first follow-up should be verifying them
  against real downloads.**
- `seat_roster`'s money is an operator assertion, one price applied to every row, no proration.
- `aws_cur` reads unblended cost only — a Savings-Plan-heavy account will not reconcile.
- **Imported figures never enter billing statements, budgets, forecasts, the optimizer or any
  enforcement path.** Reporting-only, deliberately: we will not block someone's work on a number we
  cannot verify. Whether they ever should is a policy question this ADR did not answer.
- No FX conversion; no reconciliation against a vendor invoice total; no cross-chunk dedup for an
  operator-split CUR; no split attribution for a shared account; `users.cost_center` has no history,
  so a mid-year change restates every past figure; and there is **no SPA page** (API + CSV only),
  the same posture ADR-0066 shipped with.
