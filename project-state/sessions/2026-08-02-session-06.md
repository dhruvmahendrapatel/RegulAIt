## The decisions that chose the safe side over the conventional one

**SCIM re-POST of an existing email returns 409, not 200-with-the-existing-resource.** The SCIM
convention is to return the existing resource. But a 200 would let an IdP-driven create silently
*adopt* a pre-existing local account — including an admin's. The refusal is audited as a deny.
Similarly, `DELETE /Users/:id` deactivates and the resource stays **readable** rather than 404ing,
because honoring the RFC there would destroy the audit/cost/provenance record ADR-0022 exists to
preserve.

**A role held both directly and via a group is two rows, not one row with a flag.** The composite
unique includes `origin`, so the reconciler's `DELETE ... WHERE origin='group'` addresses a
*different row* than an admin's direct grant. The rejected alternative — one row whose origin is
upgraded to `direct` — puts an ordinary `UPDATE` between an admin's grant and a sync. Losing the
admin's grant is now structurally impossible rather than avoided by correct code.

**Missing groups claim ≠ empty groups claim.** An assertion that *omits* the claim means "no
signal — do not reconcile"; an explicitly *empty* array means "member of nothing — reconcile to
zero". Conflating them converts an IdP hiccup into an org-wide access strip. SAML's
"member of nothing" is only expressible at all because node-saml sets the attribute key with an
`undefined` value when it is present-but-empty, so the check is `hasOwnProperty`, not
`!== undefined`. The honest residual — an `<Attribute>` with zero `<AttributeValue>` children is
indistinguishable from an absent attribute after XML parsing, and falls to the fail-safe — is
documented in the ADR and locked by a test.

**Three things node-saml does not do, which we now do.** It checks neither the assertion
`Recipient` nor the login-Response `Issuer` (it pins `idpIssuer` only for logout); both are checked
here, against the assertion the library *already signature-verified*, so no new
signature-wrapping surface is introduced. Its `acceptedClockSkewMs: -1` — which skips timestamp
checks entirely — is unreachable from config; skew is clamped to 0–9 minutes. And its correlation
cache is in-memory, which fails **open** across a restart or a second process, so the DB is used
instead.

**ABAC can only ever subtract.** Cedar runs *inside* the existing kernel evaluation on the allow
path only, after a grant is found — so it can never rescue an ungranted call. Locked by a test
that asserts a default-denied call stays denied even with a matching Cedar `permit`, and by a test
that an empty policy set produces byte-identical Decisions including the full `ruleChain`.

## The latent bug that would have poisoned every later slice

ADR-0038's agent hit failures that looked like its own and were not. Root cause:
`saml.test.ts` created ~30 enabled SAML providers and deleted none. Vitest orders test files by
*cached previous-run duration*, so adding any new file reshuffles the order. When saml ran before
`auth.test.ts`, auth's "sso_only cannot be enabled while zero enabled OIDC providers exist" got a
**200** — because ADR-0036 had generalized that guard to count OIDC **and** SAML together. The
assertion failed *before* the test could turn `ssoOnly` back off, so it stayed engaged, and every
subsequent password login 403'd `sso_required`: ~20 unrelated ADR-0028/0029/0030 failures
cascading from a single leak.

Fixed at the source (`19d65b3`), not by pinning vitest's order: both files snapshot and restore the
`org_settings` singleton and delete the providers they create, and auth's `sso_only` block now
*establishes* its own precondition — borrowing and disabling every enabled provider of either
family, handing them back in `afterAll` — instead of inheriting a fresh DB. Proven by reproducing
the exact cross-file ordering in separate processes against one DB: 22 auth failures before, green
after, re-proved with a third file inserted between them.

**The generalizable lesson: a test that mutates a global singleton must restore it, because the
thing that decides whether the bug fires is the order, and the order changes every time anyone adds
a test.** A second lesson sits underneath it: ADR-0036's *correct* generalization of the lockout
guard is what turned a dormant leak into a failure. Widening a guard can surface latent
order-dependence in tests that were only ever passing by luck.

## Process notes — mine

- **Subagents stopped mid-task waiting for watchers that would never wake them.** Two agents ended
  their turn saying "the monitor will re-invoke me" and simply stopped, leaving verified-but-
  uncommitted work. Resuming them worked, but from ADR-0036 onward every brief carried an explicit
  "run verification synchronously and commit yourself — no watcher will wake you", and the problem
  stopped.
- **Every agent got its own private Postgres database**, named per ADR. This was the fix for a
  session-05 failure where two agents contended on one shared `regulait_test` and produced spurious
  cross-talk. No recurrence.
- **Migration numbers were pinned in each brief** (0049…0055 assigned up front) because
  `meta/_journal.json` is the real merge chokepoint. No conflicts across six sequential slices.
- **Slices were kept strictly sequential.** Every ADR in this wave touches `schema.ts`, the
  migrations journal, and usually `auth.ts`; parallel agents would have produced merge conflicts
  rather than throughput.
