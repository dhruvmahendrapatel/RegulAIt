# Session 13 — 2026-08-09 — ADR-0073: the rules engine wired through `config_versions`

*Append-only. Never edited retroactively.*

## What this session was

One slice: close the longest-standing declared gap in the project — `PENDING.md` §3's ADR-0048 row,
*"the shadow canary for rules evaluates nothing"*. Shipped as
[ADR-0073](../../docs/decisions/0073-rules-engine-versioning.md), migration **0084**.

## The gap, stated as it actually was

ADR-0048 (migration 0060) shipped immutable versioning, canary and one-click rollback, and wired it
through the one dispatch core for exactly one artifact type: `agent_system_prompt`. That half was
and is genuinely live.

For `approval_rule`, `rate_limit`, `data_scope_rule` and `compliance_profile` it shipped **storage
only**, and said so in capitals in its own amendment. Three consequences:

1. Activating a rule version changed nothing.
2. **Rolling one back changed nothing** — the gesture an operator reaches for during an incident.
3. §2's shadow canary evaluated nothing at all, so ADR-0059's blast-radius preview had no signal to
   consume.

## What was built

- **`governedEvaluate` overlays the ACTIVE version** of every loaded rule onto its row before the
  kernel is called. `projects.ts:profilesForTags` — the one funnel every §8.3 cascade consumer
  already goes through — does the same for compliance profiles, so `projectPiiMode`,
  `projectMcpMode`, the ADR-0042 guardrail floor and the pillar-3 infra floors all inherit it
  without learning `config_versions` exists.
- **The shadow canary genuinely evaluates.** The served decision is computed to completion first,
  from the active bodies alone; then the candidate runs through the *same* kernel call parameterised
  by the candidate bodies and nothing else, and both sides land in `config_canary_observations`
  (migration 0084). `canary_pct` is honoured as a shadow **sampling rate** on ADR-0048's existing
  deterministic bucket.
- **Default-deny survives version resolution.** Versions with no active one are UNRESOLVABLE and
  deny (`config-version-unresolvable`), or 409 in the compliance path.
- **ONE indexed query per evaluation** across all three rule types — not an N+1.
- **Lazy baseline instead of a migration backfill**: the first version created for a rule mints
  `v1 (pre-versioning baseline)` from the live row.
- **Only ENFORCING columns are versionable.** A body naming a selection column (`userId`,
  `serverId`, `scope`, `tag`) is a real 422 naming what to do instead, and bodies are type-checked
  so a stored `windowSeconds: "sixty"` cannot activate and then throw on the served path.
- **SPA**: `/admin/rules` gained a shadow-canary card — every running canary with its
  sampled/would-change/failed counts, and per-decision "served vs what the candidate would have
  done, with the sentence the caller would have been given".

## The one place the brief was deliberately not followed

The brief asked for `canaryIsLive` to become **true** for rules. It has not, and the ADR says why in
its own §7.

`canaryIsLive` is read by `resolveVersion` and means *"does the canary SERVE traffic?"*. Flipping it
true for `approval_rule` would make the resolver serve the candidate — i.e. **enforce a candidate
`deny` on a percentage of real work**, which is the outage ADR-0048 §2 exists to forbid and which
directly contradicts the same brief's governing invariant that a shadow canary must never affect the
served decision. Flipping it would have closed the gap by breaking the thing the gap was protecting.

The conflation was the actual problem, so the vocabulary is split into three:
`canaryIsLive` (serves — still **false** for rules for ever, pinned by a test), `canaryIsEvaluated`
(now **true** for all four rule types) and `canaryModeOf` → `live | shadow | inert`. `inert` exists
because ADR-0048 *declared* `agent_config` a live-canary type and never wired a resolver, so for two
waves the API answered "live" about something nothing reads. It now says `inert` and "changes
nothing and measures nothing".

## Two things worth remembering

1. **The openapi drift tests caught the new routes immediately.** `openapi-registry.ts` has TWO maps
   (`ROUTE_STABILITY` and `ROUTE_TAGS`) and a new route must be in both; five tests failed until it
   was. That is the drift detection working, not noise.
2. **Shadow sampling made the first version of the new suites flaky at ~1%.** Both the artifact id
   and the user id are random per run, so a canary at 99% legitimately leaves ~1% of stable keys
   unsampled — and the first gateway run failed exactly there. Fixed in the gateway suite by choosing
   fixture ids with the *same pure bucketing function the resolver uses* (the move ADR-0048's own
   prompt suite already makes), and in the browser spec — which cannot import that function — by
   minting a fresh rule id until the subject lands inside the sample. Neither fix raises the
   percentage or weakens an assertion.
3. **A Playwright nav-link click does not remount an already-mounted route**, so the cached (empty)
   canary list was what the third spec saw. `page.goto` rather than a nav click.
4. **The seeded demo dataset already carries a fleet approval rule**, so a granted call is
   `require_approval`, not `allow`. The browser spec therefore captures whatever the baseline is and
   asserts the shadow does not MOVE it, with the candidate producing a `deny` so the divergence is
   unambiguous.

## What was disclosed rather than closed

Twelve items in ADR-0073. The three that matter most:

- **`agent_config` is still vocabulary-only.** The remaining half of ADR-0048's deviations 1/2.
- **The ordinary rule-CRUD routes do NOT mint a version**, unlike
  `POST /v1/agents/:id/system-prompt`. A versioned rule edited through the old CRUD surface has its
  row and its active version disagree, and **dispatch keeps serving the version**. This is the
  sharpest one and is named rather than fixed.
- **No pruning.** `config_canary_observations` joins `config_versions` in growing monotonically.
